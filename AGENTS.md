# Todorbit working rules

## Scope and safety

- Todorbit is a local-first Flutter productivity app targeting Windows 10/11 and Android. Windows 11 remains the primary desktop test platform. Preserve the Windows release while developing Android; see [Android acceptance and parity](docs/ANDROID.md). Keep the iOS scaffold outside this task.
- Google Drive snapshot backup/restore and incremental synchronization are approved product directions. Preserve both and keep their UX distinct; follow [Sync safety and current behavior](docs/GOOGLE_DRIVE_SYNC.md). Standard Sync and optional private encryption must retain their actual recovery requirements. Do not add unrelated cloud services, accounts, telemetry, destructive migrations or unreviewed cloud/key/ownership architecture changes.
- Preserve tasks, events, preferences, backups and widget configurations. Never reset/delete data as an error fallback. Use compatible forward migrations and transactions for multi-record edits.
- Keep planned dates, deadlines, sessions, actual work and fixed events separate. Never auto-complete or silently reschedule tasks.
- Public brand is Todorbit. Preserve `%APPDATA%\TodoPilot`, legacy `%APPDATA%\Life Manager` compatibility, native IPC names and installer AppId until a reviewed migration exists.

## Implementation

- UI belongs in `lib/features/`, domain logic in `lib/domain/`, SQLite access in `lib/data/`. Flutter database writes go through `LifeRepository` and its part files; use stable UUIDs and UTC modification timestamps.
- `AppController` coordinates shared state; profile JSON stores own device/preferences data. The native companion has a deliberately narrow database writer and never migrates schemas. See [architecture](docs/ARCHITECTURE.md).
- Follow existing Dart/Flutter conventions. Reuse nearby components, domain calculations, services and theme tokens; prefer small changes over parallel implementations.
- Follow the [Todorbit design system](docs/UI_DESIGN_SYSTEM.md) and Microsoft Fluent guidance. Identify the user journey and existing tokens, controls, and Windows/Android entry points before changing presentation. Keep visible controls functional and check keyboard access, larger text, both themes, and real Flutter rendering where practical.
- Use the [Batch 1 presentation rules](docs/UI_DESIGN_SYSTEM.md#batch-1-presentation-rules) when changing task dates, editor layout, or task action labels. Follow the [task-list presentation rules](docs/UI_DESIGN_SYSTEM.md#batch-2-task-list-presentation) for list states, grouping, and control clearance.
- Calendar changes must cover the affected Windows interactive view and Android touch agenda separately. Preserve the time-grid geometry and interaction controller contract when changing Calendar visuals. Exercise a draft through the Windows editor breakpoint and check Android keyboard clearance when editing shared EventEditor layout.
- Theme JSON is validated data only. Keep light/dark and native widget tokens synchronized; imported metadata never changes the official contributor registry.
- Show current sync state, last successful sync, and pending work independently. Verify reported conflicts against the repository review projection. Check palette changes with the native widget renderers in disposable profiles.
- Keep Focus ticks local to the timer widgets. When changing Habits or Goals, verify the selected check-in date, typed draft and named progress remain readable at Android 320 dp and 150% text. Keep temporary keyboard insets clear of save and cancel actions.
- Keep Windows runner, native widget and packaged behavior compatible. `experiments/widget-shell-probe/` is production companion source despite its name.

## Efficient workflow and verification

- Start with `git status --short` and the smallest relevant `rg` search. Exclude generated, build and dependency directories. Read only task-relevant documentation.
- Preserve unrelated uncommitted work; use a focused branch. Never reset another task's changes or move release tags. See [Codex workflow](docs/CODEX_WORKFLOW.md).
- Find the feature in [Architecture map](docs/ARCHITECTURE_MAP.md) before searching broadly. `tools/dev/verify.ps1` selects explicit Quick/Feature/Full checks; `-Plan` previews them. Never guess tests for an uncertain dependency.
- On interrupted work, inspect the current diff and latest relevant Progress checkpoint; resume pending checks against current source. Historical artifacts are evidence only for their recorded source.
- Follow [Testing](docs/TESTING.md), the persistent [test ledger](docs/TEST_RUN_LEDGER.md), and [Deferred verification](docs/DEFERRED_VERIFICATION.md):
  - **Level 1 (Fast)**: focused unit/widget tests, formatting/diff checks, and relevant static analysis (`flutter analyze --no-pub`). Run the smallest affected checks after relevant changes, reusing valid source/assertion/dependency/environment evidence.
  - **Level 2 (Critical)**: data-safety, database persistence, schema migrations, CAS tokens, sync journals, encryption, backup/restore, recurrence math, alarms, and undo/redo. Run the smallest checks covering the changed critical boundary immediately; **never deferred**. This does not require every critical suite after an unrelated UI/docs edit; valid matching evidence is reused.
  - **Level 3 (Deferred Regression)**: broader host suites, multi-module integration, cross-platform regression, and release tooling. Record in [Deferred verification](docs/DEFERRED_VERIFICATION.md); execute periodically or on-demand.
  - **Level 4 (Release Acceptance)**: Windows/Android packaging, installer/update checks, isolated profile journeys, Android 16 KiB runtime, physical device/DPI/accessibility, and real Google OAuth. Record in [Deferred verification](docs/DEFERRED_VERIFICATION.md); mandatory before release. Never treat Levels 1-3 passes as release readiness.
- **Gemini's responsibilities**: read applicable instructions and discover relevant skills; identify modified modules; run Level 1 fast tests and Level 2 critical tests; fix failures; record any deferred Level 3/4 tests in [Deferred verification](docs/DEFERRED_VERIFICATION.md); update [AI Review Queue](docs/AI_REVIEW_QUEUE.md); record test evidence and source fingerprints; never claim Codex approval or release readiness.
- **Codex's responsibilities**: inspect source changes; read [AI Review Queue](docs/AI_REVIEW_QUEUE.md); independently review Gemini's work; fix confirmed issues; reuse valid test evidence matching exact source fingerprints; run additional targeted checks justified by risk; review critical deferred items in [Deferred verification](docs/DEFERRED_VERIFICATION.md); archive approved items to [AI Review History](docs/AI_REVIEW_HISTORY.md); preserve incomplete verification in [Deferred verification](docs/DEFERRED_VERIFICATION.md); never repeatedly run unchanged broad suites.
- **Separation of tracking**: [AI Review Queue](docs/AI_REVIEW_QUEUE.md) tracks unreviewed code changes; [Deferred verification](docs/DEFERRED_VERIFICATION.md) tracks unfinished tests and acceptance checks. An empty code-review queue does not imply release readiness.
- Use connected Dart/Flutter MCP diagnostics and live inspection when relevant. Visually verify UI in an isolated profile when practical. Never test against personal data; verify child-process `APPDATA`, `LOCALAPPDATA` and resolved profile first.
- Native painting, shell attachment, input, DPI or menu changes require native Release/self-test plus the relevant [manual widget checklist](docs/windows-widget.md). Automated tests do not prove physical Windows behavior; report unobserved behavior accurately.
- Review diffs and run `git diff --check`. Do not commit builds, caches, secrets, credentials or machine-specific settings.
- Do not publish a release unless explicitly requested. Preserve version synchronization, CI, installer, updater and checksum gates in [release preparation](docs/RELEASE.md). Documentation-only work needs no version bump or package rebuild.

## Skills and documentation routing

- Any backend, domain, data persistence, SQLite/Drift migration, synchronization, encryption, native Windows/.NET or Android/Kotlin interop, background alarms, lifecycle, memory/CPU performance, or architectural code work MUST route to the canonical [Todorbit Engineering Quality](.agents/skills/todorbit-engineering-quality/SKILL.md): read it before modifying architecture or persistence logic and apply its data-safety (zero data loss, forward migrations, CAS concurrency tokens), 16GB host resource limits, root-cause diagnosis, and context-efficiency rules.
- Any UI/UX impact MUST route to the canonical [Ultimate UI/UX](.agents/skills/ultimate-ui-ux/SKILL.md): read it before design or UI changes and apply it during implementation and verification. This includes creation, features, fixes, refactors, performance work, reviews/tests/audits; screens, dialogs/popups/menus/sheets, controls/forms/validation/navigation, typography/color/spacing/sizing/icons/motion, themes/personalization, responsive behavior, localization/RTL/semantics/accessibility/input, and Flutter or native Windows/Android widgets/interfaces. State, async, backend or service work also qualifies whenever it changes displayed values, feedback or journeys such as loading/saving, Sync, authentication, backup, recovery or errors. Task labels never exempt UI impact. Unrelated backend work does not require this skill or a UI audit. Before creating new UI elements or modal dialogs, inspect `lib/features/shared/` (`AppLayout`, `AppSpacing`, `AppModalShell`, `AppTaskRow`, `SettingsSection`, `TodorbitThemeTokens`) and reuse existing components, layout breakpoints, and semantic tokens rather than inventing duplicate controls or hardcoding dimensions.
- Follow the [UI quality workflow](docs/CODEX_WORKFLOW.md#ui-quality-workflow): identify affected platforms, surfaces, states and journeys; load only relevant skill references; inspect both implementation correctness and experience quality; verify functionality/usability and report evidence plus untested areas. A complete app audit is required only when requested or justified by scope. Reuse the loaded skill within a session unless it changes or context is unavailable. There is one canonical Todorbit UI skill; other design/framework skills supplement it, with platform standards and Todorbit tokens authoritative.
- Use `.agents/skills/todorbit-regression/SKILL.md` for code validation/release checkpoints; use specialized Dart/Flutter or other skills only when they materially help. Do not load every skill. Windows guidance and Todorbit tokens remain authoritative for this app. Testing documentation (`docs/TESTING.md`, `docs/TEST_RUN_LEDGER.md`) remains the sole authority for verification execution and evidence records.
